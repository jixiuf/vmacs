# 全局规则

## 响应语言

所有返回给用户的消息（含思考过程、分析推理、代码审查、重构计划、工具调用理由）**必须使用中文**。

### Elisp 项目代码规范

仅Elisp 项目中（含 `.el` 文件的仓库），源代码**禁止出现中文字符**：

- 工程文件（`.el`, `.elc`, `Makefile`, `Cask`, `README`, `AGENTS.md` 等）不得含中文。
- 注释、docstring、错误消息、用户提示、标识符全部使用英文。
- 例外：涉及中文内容的测试用例可含中文字符串数据，但测试代码本身的注释和结构仍需用英文。

### Go 项目代码规范
- 注释、docstring、错误消息、用户提示、标识符推荐使用中文。

## 问题排查方法论 (RCA)

### 核心原则

- **证据先行** — 结论必有可验证数据支撑，拒绝猜测。
- **追问补缺** — 信息不足时主动提问，不脑补细节。
- **多假设验证** — 提出 3-5 个假设逐一检验，避免确认偏误。
- **验证标准**：自问"修复后问题会复发吗？能解释所有症状吗？"

### 工具

5 Whys、Fishbone、Fault Tree Analysis、Timeline 重构、Change Analysis、相关性分析。

### 步骤

1. 收集证据（日志、指标、配置、时间线）→ 2. 生成 3-5 个假设 → 3. 逐一验证/推翻 → 4. 确认根因（证据充分时才下结论）→ 5. 制定修复与预防方案。最终输出：问题定义 → 证据 → 假设 → 分析 → 根因 → 方案 → 待办。

### 反模式对照

| 反模式 | 正确做法 |
|--------|---------|
| 崩溃函数包 try/catch | 追溯数据/类型/生命周期根因并修复 |
| `(when x ...)` 防 nil | 跟踪赋值链，消除 nil 源头 |
| 快速给出看似合理的解释 | 多假设验证后确认根因 |

## 重构最佳实践

### 先读后写，先计划后执行

理解全貌再动手。复杂变更先在只读模式下探索代码、生成计划，确认方案后再编辑。
任何修改（含重构）前必须先读当前代码——项目演进中，调用方/参数/约定
随时可能变化，本文件与 skill 文档都只是快照，**当前代码才是唯一真相**。禁止凭记忆或
旧文档直接动手。

```markdown
1. 先阅读：[相关文件]
2. 理解调用图和数据流，提出方案（含风险区域、迁移策略）
3. 确认后再实现
```

### 别猜测 不确定（字段名/参数值/URL 参数/接口行为）时，先 grep 当前代码确认，而不是按印象写。

 发现问题至少问一下：读到与认知不符的代码、或发现疑似冲突/回归，先停下来向用户
   确认，不要自作主张改回去或猜着补。
   
   
### 增量可逆

每步自洽且独立可回退。产出干净的 `git diff`，通过 `make compile && make test`（如有）。

```markdown
分 3 阶段，每阶段确认后继续：
1. 纯抽取，不改逻辑
2. 适配调用方
3. 删除旧代码
```

### 范围纪律

重构中发现无关 bug 或风格缺陷：**不要顺手修复**，仅记录（`TODO` 等），询问是否分开处理。若与重构纠缠则声明在范围内。

### 验证闭环

给 agent 可跑的 check（测试/lint/构建），执行后读取结果，失败则继续迭代。"看着像好了"不可信。

修改完成后 review diff 确认是否有不该留下的临时改动 (用户做的修改不要动)
